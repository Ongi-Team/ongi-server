# PR 설명 자동 생성 가이드 (for claude)

## 📌 목적

현재 브랜치(`develop` 기준 diff)를 분석하여 팀 PR 템플릿에 맞는 설명을 자동으로 작성합니다.

---

## 실행 절차

1. `git log develop..HEAD --oneline` 으로 커밋 목록 확인
2. `git diff develop...HEAD --name-only` 로 변경 파일 목록 확인
3. 주요 변경 파일의 내용을 읽어 작업 맥락 파악
4. 아래 템플릿에 맞게 PR 설명 작성

---

## 출력 형식 (팀 PR 템플릿)

아래 템플릿을 **그대로 출력**합니다. 괄호 안 설명은 실제 내용으로 채우고 제거하세요.

```markdown
## #️⃣ 관련 이슈

closed #[브랜치 이름에서 숫자 추출. 예: feat/#37 → 37]

## PR 유형
어떤 변경 사항이 있나요?

- [x or 공백] 새로운 기능 추가
- [x or 공백] 버그 수정
- [x or 공백] 코드 리팩토링
- [x or 공백] 주석 추가 및 수정
- [x or 공백] 문서 수정
- [x or 공백] 테스트 추가, 테스트 리팩토링
- [x or 공백] 빌드 부분 혹은 패키지 매니저 수정
- [x or 공백] 파일 혹은 폴더명 수정
- [x or 공백] 파일 혹은 폴더 삭제

## PR Checklist
PR이 다음 요구 사항을 충족하는지 확인하세요.

- [x] 커밋 메시지 컨벤션에 맞게 작성했습니다.
- [x or 공백] 변경 사항에 대한 테스트를 했습니다.(버그 수정/기능에 대한 테스트).

## 🧩 작업 내용

[변경의 배경과 목적을 1~2문장으로 요약. "무엇을" 보다 "왜"를 중심으로 작성]

### 변경 사항

[파일/클래스/메서드 단위로 변경 내용을 bullet point로 정리. 코드 설명보다 의도 중심으로]

### 동작 흐름 (선택 — 플로우가 복잡할 때만)

[필요한 경우 화살표(→) 형식으로 요청/이벤트 흐름 표현]

## 📸 스크린샷(선택)

해당 없음

📣 **To Reviewers**

---

[리뷰어가 특별히 주의해야 할 사항, 설계 결정 배경, 사이드 이펙트 가능성 등을 간략히 기술. 없으면 섹션 내용 비움]

- Reviewers : 팀 선택
- Labels : [커밋 타입 기반으로 feat / fix / refactor / chore 중 해당하는 것 나열]
```

---

## 작성 규칙

- **이슈 번호**: 브랜치명(`feat/#37`)에서 숫자를 추출. 브랜치명에 숫자가 없으면 `#이슈` 그대로 유지
- **PR 유형 체크박스**: 실제 변경 파일과 커밋 타입을 기준으로 해당 항목에만 `x` 표시
- **테스트 체크박스**: `src/test` 경로에 변경된 파일이 있으면 `x`, 없으면 공백
- **작업 내용**: 커밋 메시지를 그대로 나열하지 말고, 변경의 맥락과 이유 중심으로 재구성
- **동작 흐름**: 이벤트 발행, 스케줄러, 외부 연동 등 흐름이 복잡한 경우에만 추가
- **To Reviewers**: 삭제/교체된 클래스, 설계 결정, 주의할 사이드 이펙트가 있으면 명시. 없으면 내용만 비움 (섹션 자체는 유지)
- **Labels**: 커밋 타입 집합으로 결정 (feat 커밋 있으면 `feat`, fix 있으면 `fix` 등)
- 마크다운 코드블록(```) 없이 **바로 복사해서 쓸 수 있는 형태**로 출력
